这些值描述此机器、配置与预热后的空闲 runtime。独立测试 `idle_1` 为 2,880 KiB 增量，而完整矩阵为 32 KiB，说明固定初始化和分配器保留显著影响单会话样本；不能推广“每个 session 固定 200KB”。未提高 fd 上限的早期运行已真实失败，不能从那份报告推导千会话容量。

`replay_100k` 的 reader 耗时 29.051ms、runtime 启动 135.325ms、首 turn 435.544ms；RSS 基线 259,744 KiB、采样峰值 893,600 KiB。预读的完整历史 rows 在后续测量期间仍存活，且各用例复用同一进程，因此峰值不等于生产会话的独立稳态占用。

## 解释边界与待验证项

- `sse_10k` 收到 10,009 个 runtime 事件，流 backlog 丢弃为 0，约 414,119 events/s；这是内存 mock 事件交付，不是 HTTP SSE parser/网络吞吐。日志同时记录磁盘诊断事件队列满，不能宣称所有事件通道无丢失。
- `compact_10/100` 分别使用 64/604 个 turn、10/100 次摘要 backend 请求，整段耗时 0.923/8.871s。按旧字段相除得到 92.276/88.706ms；包含普通 turn 与启动，旧报告也未逐次证明 checkpoint 发布，不能称为纯压缩延迟。
- 并发 32/64/128 的吞吐分别约 20.263/20.465/19.197 tasks/s；每个任务新建 runtime、执行一轮并 shutdown。不是已启动 session 的稳态问答吞吐，单次矩阵也不能据此断言锁回归。
- `subagent_fanout_2/4/8` 旧样本仅记录父 turn `Ok` 与调用数 2/4/8，没有子代理成功数或 backend 子请求计数，不能据 9.651–10.806ms 证明全部子任务执行成功。新套件增加子请求/工具错误核对；旧数字保持原样。
- 归档时针对纳入前的 mock 新增验证，实测 `subagent_requests=0`：mock 只填 `input_json`，但 runtime 交接从 `fields.prompt` 取子任务。套件现同步填充 fields 并核对子请求数，因此旧扇出项不作为成功扇出的性能基线；原 dirty tree 未保存，不据此断言其所有其他实现细节。
- `sandbox_start` 有 10 个样本、`sandboxed=true`、诊断列表为空，p50 79.815ms；内部启动 p50 31.505ms、内部 turn p50 9.982ms。旧字段未记录逐次成功数，新套件补充成功/请求计数后才能更严格比较。

此记录用于提出后续测量问题，不设跨平台性能承诺。比较改动时应在相同配置与源码状态下分别复测；单次 smoke 验证只证明套件可执行，不作为新的性能基线。
