# PTC 模式收益实测（云 API）：2026-11-27

> 维护记录，不进入官网发布产物。本页对比同一编码/分析问题下关闭 PTC（`off`，3 组均值）与开启 PTC（`tool`，5 组均值）的云端实测表现。

测量方法与索引见[性能与验证](../performance.md)。

## 核心对比（`off` vs `PTC`）

| 指标 | 关闭 PTC（`off`） | 开启 PTC（`tool`） | 变化 |
|---|---:|---:|---|
| 工具结果回传总量 | 79.7KB | **18.9KB** | **−76.3%**（Python 侧过滤聚合，仅回传摘要） |
| 非缓存 input | 40.4k | **14.9k** | **−63.3%** |
| **总 prompt** | 185.3k | **81.4k** | **−56.0%** |
| `output`（含代码约 280 tokens） | 2,382 | 2,713 | +13.9% |
| 云 API 墙钟 / LLM 请求 | **16.8s** / 6.0 次 | 18.2s / 7.0 次 | +8.5%（多 1 次编排轮次） |

## 结论

- **显著降低上下文与输入成本**：PTC 在 Python 宿主侧完成数据筛选与结构化抽取后，工具回传体积压缩 **76.3%**，直接带动非缓存 input 下降 **63.3%**、总 prompt 下降 **56.0%**。
- **可预期的延迟权衡**：由于模型需要额外生成约 280 tokens Python 编排代码并多出约 1 次请求，单任务墙钟略增 `1.4s`（`+8.5%`）；在工具输出较大或需多步过滤聚合的任务中，Token 节省收益远大于小幅墙钟增量。
